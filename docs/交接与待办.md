## 一、换机后第一件事：私钥不在仓库里

**`tools/keys/private.pem` 被 `.gitignore` 排除，clone 下来是没有的。**

它是**全世界唯一**能签出有效激活码的文件。新电脑上没有它：

- ❌ `node tools/gen-key.mjs` 发不出激活码
- ❌ `npm run test:desktop` 会失败（签发/验签对不上）
- ✅ 软件本身照常跑（验签用的是硬编码在 `electron/license.js` 里的公钥）

### 怎么办

**正确做法：把老电脑上的 `tools/keys/private.pem` 用 U 盘拷过来**，放回同样路径。
不要走微信、网盘、邮件——这个文件泄露等于任何人都能给自己发激活码。

**千万别做的事：在新电脑上跑 `node tools/init-keys.mjs --force`。**
那会生成一对新密钥并改写 `electron/license.js` 里的公钥，结果是
**所有已经发出去的激活码全部失效**。这个坑本项目已经踩过一次。

### 现在有几份（2026-08-06）

开发机上另外放了两份（权限已收紧为仅本人可读写，各带一份说明 txt）：

- `C:\Users\<用户名>\AppData\Roaming\觅客舵-密钥备份\private.pem`
- `E:\觅客舵-密钥备份\private.pem`

怎么确认某一份没坏、且是对的那一把——推导公钥，必须等于
`electron/license.js` 里的 `PUBLIC_KEY_B64`（对不上会导致 `test-desktop`
全挂，历史上栽过一次）：

```bash
node -e "const c=require('crypto'),f=require('fs');const p=c.createPrivateKey(f.readFileSync('tools/keys/private.pem','utf8'));const d=c.createPublicKey(p).export({type:'spki',format:'der'});console.log(d.subarray(d.length-32).toString('base64'))"
```

> 脱机备份（U 盘）当时手边没有可移动介质，**仍待补**。

#### 2. SPA 官网 —— ✅ 已如实告知（2026-08-19），彻底解决仍未做

**已做**：抓取时判断这一页是不是 JS 渲染出来的空壳，并据此说两句完全不同的话。

- 判据：框架特征（空的 `#root`/`#__next` 容器、`__NEXT_DATA__`、Nuxt、Angular、
  React、Wix、Shopify、Squarespace）+ 正文长度；另有一条兜底（正文极少而脚本很多）
- **服务端渲染过的 React 不会被误判**——有框架特征但正文够多就照常抓
- 空壳站的提示改成：「官网是动态渲染的（…），内容要浏览器跑完脚本才出现，
  我们抓到的是空壳——**这不代表对方没公示联系方式**。建议手动打开看一眼，
  或改用 Hunter / 邮箱查找 Webhook。」
- 批量抓取的汇总里空壳站单独计数，不混进"没抓到"

原来那句「抓了 N 页，没有公示邮箱」会让用户以为是对方没写，**顺手把好线索删掉**。

**仍未做（真正的解决）**：用 Electron 的隐藏 `BrowserWindow` 加载页面、等 JS 跑完
再取 DOM。技术上可行（约 60 行），但要处理超时、内存、弹窗、下载拦截，
并且要串行化以免同时开一堆窗口。**只在检测到 spa 时才触发**，成本可控。
做不做取决于第 1 条（覆盖率实测）的结果——如果空壳站占比很低，就不值得做。

#### 3. ~~RCPT 探测没在真实网络下跑通~~ ✅ 已实测（2026-08-21）

**先纠正一个错判**：这条待办原来写「开发机出站 25 端口被封」，那是错的。
当时是**沙箱 DNS 解析不出 MX**，我把它误判成端口封锁。实测 25 端口是通的
（gmail / qq 都能握手）。

实测跑通后暴露两个真 bug，都属于「把测不出说成了确定结论」这一类：

**① MX 查询还在用裸的系统解析器** ——`domainHealth` 早就改成多解析器了，
`verifyEmail` 漏掉了。结果 `github.com` / `qq.com` 被判成「没有 MX 记录，
收不了信」。而 `invalid` 在 F3 里是**一票否决**：DNS 一抖，用户所有邮件
都会被拦，理由还是错的。现在走 `mxChecked`，并区分「有解析器明确说没有」
（invalid）与「谁都没答上来」（unknown）。

**② 550 不等于 550。** 真网实测拿到两条原文：

```
github.com → 550 5.7.1 ... Client host [x.x.x.x] blocked using Spamhaus
qq.com     → 550 Mailbox not found
```

前者是「你的 IP 被拉黑了，我不跟你说话」，跟地址存不存在毫无关系；
后者才是「这个地址不存在」。原实现只看状态码，会把前者判成 invalid，
**把真客户的地址拉黑**。现在按应答正文分类：blocked / invalid / unknown。

**③ 一个必须知道的现实**：家用与办公宽带的出口 IP 常年在 Spamhaus 之类的
公共黑名单上（开发机就是），所以对大厂邮箱的探测多数会返回 blocked。
这不是 bug，是这条路的固有局限。现在批量探测结束时会把原因讲一次：
「你的出口 IP 在 Spamhaus 黑名单上……这不是地址有问题，也不是软件坏了」，
并给出替代方案（配 Hunter / 换出口线路）。

**结论**：RCPT 探测对自建域名和中小企业邮箱有效，对大厂邮箱多数测不出。
它的定位应该是「能测出来的算白赚，测不出不影响原有判定」，
而不是主要的验证手段——README 与界面措辞已按这个口径。

#### 4. ~~「零配置」这个说法兑现不了~~ ✅ 已改叙事（2026-08-21）

**结论：不再宣称「零配置」，改成把两段式现实和真实价钱摊开写。**

因为「零配置」这句话其实**对第一封信是成立的**——粘贴 Google 搜索结果 +
抓官网拿联系方式 + 填自己的 SMTP，一个 key 都不用。上手向导的五步就是这条路。
不成立的是把它泛化到整个产品：跑量要 SerpAPI，AI 写信读信要模型 key。

含糊过去的后果是用户走完五步之后**突然撞上收费墙**。所以现在：

- 向导副标题限定范围：「这五步不用配任何 API key……要跑量、要 AI 写信才需要配」
- 向导底部新增成本表，逐项写清免费/收费，AI 那行直接写 **≈¥14/月**
  并给 DeepSeek 与 SerpAPI 的申请链接，旁边显示「已配/未配」
- 明说没有「内置额度」，并给理由：`.asar` 可解包，内置我们的 key 等于送给所有人
- README 新增「要花多少钱」一节，同一套口径

`test-netprobe` 加了三条测试守住这件事：成本表不许被删、AI 月成本必须写出来、
副标题必须限定在「这五步」而不能泛化成整个产品。

**仍然不建议的两条路**（架构上冲突，不是没想到）：
- 自建中转垫额度 → 就有服务端了，和「纯本地 + 买断」的定位冲突
- 内置我们自己的 key → asar 可解包

给了两份能直接粘的端点实现 + 一份搭建文档，都随包发货：

两个实现上的决定：

- **像素 URL 只带 outbox id，绝不带收件人邮箱。** 邮件源码是收件人可见的，
  中间每一跳也可见；把邮箱写进 URL 等于当面泄漏，还会被反垃圾系统当成
  典型追踪特征。为此把事件匹配从「只认邮箱」扩成「id 优先、邮箱兜底」。
- **像素路径不校验 token，拉取路径必须校验。** 邮件客户端请求像素时带不了
  token；但 `/events` 不校验的话，任何人都能拉走你客户的打开记录。

文档里如实写了打开率天然不准（Gmail/Outlook 预取会虚高、客户端屏蔽图片会
虚低），以及它在软件里只用于「打开 ≥3 次未回复」的排序——这个用法对误差不敏感。

端到端验过：起一个本地端点，像素请求 3 次 → 拉取回 3 条事件 → 打开次数 3 →
行为分支正确落到「打开 ≥3 次但没回」。无 token 拉取返回 403。

### 🟡 P2：该做但不急

#### 9. ~~内置数据集会过期，但没有更新机制~~ ✅ 已解决（2026-08-19）

做法是「随版本重建 + 应用内陈旧提示」：

- `node tools/check-data-age.mjs` 是发版硬前置，超过告警线退出码为 1
- 阈值按各自更新频率分开定：制裁名单 90/180 天，采购官库 180/365 天，
  HS 目录 730/1460 天

## 四、代码走查

```bash
node tools/audit.mjs
```

查的都是**静默失效**类问题——不报错、看着对、就是不工作。发现问题退出码为 1。

八项：同名函数重复定义 / 「包一层」包错名字 / 死代码 / `elements.xxx` 指向不存在的
DOM id / IPC 三方对不上 / 线索字段写了没人读 / 源码里的控制字符 /
`admitProspects` 之后必须同步写回 `state.prospects`。

最后一项是个容易被后人破坏的真不变量：`admitProspects` 内部会触发入池体检
（抓官网核实公司存在 + 合规筛查），那段是 fire-and-forget 的微任务，
**依赖调用方在同一个同步块里把线索写进 `state.prospects`**。
中间插一个 `await`，微任务就会先跑，那时线索还不在池子里，体检什么都找不到
——而且不报任何错。

**首次跑就抓出五个真问题，全是「功能做了一半」：**

| 问题 | 后果 |
|---|---|
| `screeningPanelHtml` 写好了从没挂载 | 合规命中详情**永远看不到**；拦是拦住了，但用户不知道命中哪条法律线 |
| `renderCommerceChrome` 没有 try | 它一抛错，上面九个面板**全部不渲染**，而且是静默的 |
| `sequencePausedReason` 只写不读 | 序列悄悄停了，用户既看不到状态也不知道原因 |
| `websiteConfidence` / `websiteNote` 只写不读 | 「AI 推测」和「联网核实」在界面上长得一样，用户没法判断该不该信 |
| `test-import.mjs` 里的 `capitalize` 桩含控制字符 | 那个桩**什么都没做**，等于测试跑的不是真逻辑 |

顺带把 09 里的**六层 `render` 包装合并成一层挂载表**。层数多有两个坏处：
读代码要顺着六层才知道一次渲染干了什么；更要命的是任何一层在 try 外面抛错，
上面所有层都不再执行——而这种失败没有任何提示。

### 第二轮深挖（2026-08-21）：状态机 / 数值口径 / 异步竞态

这三类查完**没有发现新的真问题**，但过程本身值得记下来，省得以后重查：

**状态机**——把所有被写入的 `status` 值和所有被判断的值两边对齐，
四组「判断了但没人写」全是假阳性：`invalid`/`valid` 由 `electron/netprobe.js` 写、
`level` 的三个值由 `dataset-age.js` 写（跨进程，扫 `src/` 看不到），
`all`/`done` 是 index.html 里的下拉选项值。

**唯一需要处理的**：`contactSource === "claude" / "local"` 现在没有任何代码会写出来
——那两条编造联系人的路径已经删了。但老用户数据里还有，所以这条判断必须留着。
已在代码里写了注释，防止被当死代码删掉。

**数值口径**——全项目 10 处过滤 `status === "已发送"`，写法完全一致，
且都不排除退信。这是对的：退信也占用了发送额度和预热配额，
而退信率的分母本来就该是「发出去的总数」。

**异步竞态**——12 个 `admitProspects` 调用点全部同步写回（已固化成第 ⑧ 项检查）。
另外三处「快照跨 await 写回」的疑似模式，逐个看下来都安全：
`probeProspectEmail` / `screenProspect` 写回时是 `state.prospects.map()`
**重新读当前 state**，快照只用来读 `.email`；`findLookalike` 里那个 `await`
在 `if (aiEnabled())` 分支中直接 return 了，写 state 的代码根本到不了。

> 第 ⑦ 项（控制字符）是被自己坑出来的：写这个走查工具时，
> `//` 又被吃成了 `U+0008`，导致 ④ 误报 200 多处。
> **本项目已经栽过六次**。规律：`` `` `
` 这类本身是合法转义的序列会被吃掉，
> `\s` `\d` `\W` 不会。写正则时优先用字符类，或者干脆用 `String.fromCharCode`。

### 第三轮（2026-08-22）：规模性能 —— 线索池上千条会不会卡

**结论：以前会，现在不会了。** 真机实测（Chrome，`node tools/bench-scale.mjs` 是配套的离线基准）：

| 视图 | 1000 条 | 2000 条 | 5000 条 |
|---|---|---|---|
| 工作台 | 92 → **15ms** | 347 → **11ms** | 2465 → **33ms** |
| 潜客页 | 290 → **57ms** | 614 → **63ms** | 1644 → **78ms** |
| CRM 看板 | 223 → **28ms** | — → **29ms** | 1344 → **45ms** |
| 分析页 | 41 → **23ms** | — → **67ms** | 526 → **389ms** |
| 发信队列 | 111 → **108ms** | 232 → **195ms** | 623 → **469ms** |
| 收件箱 | 82 → **87ms** | — → **164ms** | 459 → **451ms** |

问题分两类，修法完全不同。

**第一类：算法平方级。** 「这条线索回过信没 / 开过信没 / 发过没 / 对应的线索在哪」
这几个问题被反复问，而每问一次就 `some()`/`find()` 扫一遍全表，问的次数又跟线索数成正比。
`isReplied` 在一次渲染里被调 3465 次，每次扫一遍全部来信。修掉六处：

- `computeLeadScore` 的互动信号（3 处内联扫表 + `hasSentOutbound`）
- `preflightOutboxItem` —— **三层各查一遍同一条线索**（基础实现 + 08 的 F3 包装 + 09 的合规包装），
  「包一层」这个模式的固有代价：每层都独立重新查一次
- `funnelFor` —— 五个 `prospects.filter(p => outbox.some(...))`。注释写着「漏斗算法只此一份」，
  所以这一处平方级同时拖慢分析页、渠道对比、来源效果、转化协助一整片
- `isReplied` / `replyChannels`
- `dueFollowupProspects`（工作台待办每次都调）
- `active*` / `ax*` 那一族派生集合 —— 86 个渲染函数都在调，每次重新过一遍全池

做法是**渲染期索引**（`src/0-brand-edition.js` 的 `buildScanIndex` / `renderMemo`）：
渲染开始时各扫一遍建索引，之后每次查 O(1)，渲染一结束立刻丢掉。

> 关键是**生命周期只限一次同步渲染**，不做长期缓存。
> 发送会把 outbox 条目的 status 就地改成"已发送"，数组引用和长度都不变，
> 任何「按引用+长度」的失效判据都会失灵，质量分会一直停在发送前的旧值。
> 不在渲染中时索引为 null，各处自动退回原来的扫表写法，行为完全一致。

**第二类：DOM 节点爆炸。** 这类优化 JS 一点用没有。潜客页 2000 条线索会生成
**3.4 万个 DOM 节点、2.2MB HTML**，其中拼字符串 164ms、写 innerHTML 51ms，
而浏览器**强制排版 540ms**。修法是不生成这么多节点：

- 潜客表每次渲染 200 行，其余「再显示 200 条 / 全部展开」
- CRM 看板每列封顶 60 张卡，列头的数量和金额仍按全部算
- 发信队列封顶**已处理**的那部分

> 分页最容易踩的坑是**静默改掉「全选」的口径**。原本 `visibleProspectIds()` 是数
> DOM 里有几个复选框，一分页就会从「全选当前筛选结果」悄悄变成「全选当前页」，
> 而界面文案一个字没变。现在完整的筛选结果 id 记在 `mkdFilteredProspectIds` 上，
> `bench-scale.mjs` 里有专门的守卫盯着这一条（改坏了退出码 1，已验证过它真的会失败）。

**故意没做的：发信队列的整体分页。** 它的勾选状态存在 DOM 的复选框上而不是 state 里，
整体分页会让「全选待审/待发 (N)」只选当前页。要正确做，得先把勾选搬进 state
（像潜客页的 `mkdSelectedProspects` 那样）。所以只封顶了不带复选框的已处理条目，
2000 条时降到 195ms —— 够用但不算快，剩下的 333 封待审待发是**必须**全渲染的。

**分析页 5000 条 389ms**：调用次数已全部是线性的（实测 ×4 数据 → ×4 调用），
剩下的是分配/GC 的量级效应，不是算法问题。1000~2000 条时只有 23~67ms，真实规模下不构成问题。

### 值得记住的坑（都已修掉并写进测试，别踩回去）

1. **国内 DNS 返回残缺 TXT**。查 github.com：系统默认 8 条无 SPF、8.8.8.8 22 条有
   SPF、阿里 223.5.5.5 17 条无 SPF。据此让已配 SPF 的用户"再加一条"，两条 SPF 按
   RFC 7208 直接失效——**会亲手搞坏用户的送达率**。现在多解析器取并集 + 查不准就说查不准。

2. **没配追踪时 `opens` 恒为 0**，`cold` 分支会把所有人判成"没打开"并自动暂停全部序列。
   **测不到 ≠ 没打开**。

3. **定位校准会误伤用户自己的产品词**。卖无人机配件的人标记一家无人机工厂为不对口，
   `drone` 进排除词就等于废掉他的全部搜索。现在有 `protectedTerms()` 保护。

4. **合规筛查剥词要有分寸**。剥 `CO/LTD/GmbH` 是对的（让"少个逗号"不影响比对），
   但**不能剥** `TRADING/HOLDING/INTERNATIONAL`——那样 `ACME TRADING` 和
   `ACME HOLDINGS` 会一起压成 `ACME` 双双误报。误报和漏报一样有害。

5. **`noticedate` 是 `DD-Mon-YYYY` 文本**，按字符串比大小会算错
   （`'04-Aug-2026' < '31-Oct-2025'`）。我用它得出过一次错误结论。

6. **JS 模板字符串里的 `` 是退格符不是词边界**。`new RegExp(\`\b(...)\`)` 少一个
   反斜杠，正则里就没有词边界，规则**静默失效**（不报错、看着对、就是不生效）。
   合规筛查的剥词最后改成了 token 过滤，绕开这类转义坑。

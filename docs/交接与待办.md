## 一、换机后第一件事：私钥不在仓库里

**`tools/keys/private.pem` 被 `.gitignore` 排除，clone 下来是没有的。**

它是**全世界唯一**能签出有效激活码的文件。新电脑上没有它：

- ❌ `node tools/gen-key.mjs` 发不出激活码
- ❌ `npm run test:desktop` 会失败（签发/验签对不上）
- ✅ 软件本身照常跑（验签用的是硬编码在 `electron/license.js` 里的公钥）

### 怎么办

**正确做法：把老电脑上的 `tools/keys/private.pem` 用 U 盘拷过来**，放回同样路径。
不要走微信、网盘、邮件——这个文件泄露等于任何人都能给自己发激活码。

**千万别做的事：在新电脑上跑 `node tools/init-keys.mjs --force`。**
那会生成一对新密钥并改写 `electron/license.js` 里的公钥，结果是
**所有已经发出去的激活码全部失效**。这个坑本项目已经踩过一次。

### 现在有几份（2026-08-06）

开发机上另外放了两份（权限已收紧为仅本人可读写，各带一份说明 txt）：

- `C:\Users\<用户名>\AppData\Roaming\觅客舵-密钥备份\private.pem`
- `E:\觅客舵-密钥备份\private.pem`

怎么确认某一份没坏、且是对的那一把——推导公钥，必须等于
`electron/license.js` 里的 `PUBLIC_KEY_B64`（对不上会导致 `test-desktop`
全挂，历史上栽过一次）：

```bash
node -e "const c=require('crypto'),f=require('fs');const p=c.createPrivateKey(f.readFileSync('tools/keys/private.pem','utf8'));const d=c.createPublicKey(p).export({type:'spki',format:'der'});console.log(d.subarray(d.length-32).toString('base64'))"
```

> ⚠️ **仍未解决：这三份在同一块物理硬盘上**（开发机的 C/D/E 是同一块
> Samsung 870 EVO）。所以现在只防得住误删和误 `git clean`，**防不住硬盘损坏**。
> 脱机备份（U 盘）当时手边没有可移动介质，**仍待补**。
>
> 明确不走网盘：机器上的 OneDrive 是学校账号，明文签名私钥不上第三方云端；
> 真要走网盘必须先加密再传。

#### 1. ~~官网抓取的真实覆盖率没验过~~ ✅ 已实测（2026-08-19）

`node tools/coverage-test.mjs 清单.txt`（输入格式随便，含粘贴的搜索结果）。

20 个真实海外买家官网，用产品自己的方法生成，6 品类 × 6 市场：

| 指标 | 实测 |
|---|---|

| 拿到邮箱（占能打开的） | **68.8%** ← README 写的 ≥60% 站得住 |
| 拿到同域邮箱 | 62.5% |
| 拿到电话 | 81.3% |
| 拿到 WhatsApp | 43.8% |
| 邮箱或电话至少一个 | **93.8%** |

**样本只有 20 个，置信度有限。** 有真实客户名单时应该再跑一次 50–100 个确认。

三个直接影响决策的发现：

1. **电话比邮箱更容易拿到**（81.3% vs 68.8%），WhatsApp 43.8%。产品叙事不该
   只讲邮箱——中小买家官网留电话比留邮箱普遍，而外贸本来就重 WhatsApp。
2. **一个 SPA 站都没有** → 第 2 条里说的「隐藏 BrowserWindow 渲染」**不值得做**。
   发展中市场的中小进口商官网基本是老派静态 HTML。
3. 跑这次实测时抓出一个真 bug：电话提取把 `20250909`（日期）和 `00512512`（编号）
   当成了号码，「拿到电话」虚高到 87.5%。修完是 81.3%。
   **不实测就会拿着虚高的数字去写销售页。**

#### 2. SPA 官网 —— ✅ 已如实告知（2026-08-19），彻底解决仍未做

**已做**：抓取时判断这一页是不是 JS 渲染出来的空壳，并据此说两句完全不同的话。

- 判据：框架特征（空的 `#root`/`#__next` 容器、`__NEXT_DATA__`、Nuxt、Angular、
  React、Wix、Shopify、Squarespace）+ 正文长度；另有一条兜底（正文极少而脚本很多）
- **服务端渲染过的 React 不会被误判**——有框架特征但正文够多就照常抓
- 空壳站的提示改成：「官网是动态渲染的（…），内容要浏览器跑完脚本才出现，
  我们抓到的是空壳——**这不代表对方没公示联系方式**。建议手动打开看一眼，
  或改用 Hunter / 邮箱查找 Webhook。」
- 批量抓取的汇总里空壳站单独计数，不混进"没抓到"

原来那句「抓了 N 页，没有公示邮箱」会让用户以为是对方没写，**顺手把好线索删掉**。

**仍未做（真正的解决）**：用 Electron 的隐藏 `BrowserWindow` 加载页面、等 JS 跑完
再取 DOM。技术上可行（约 60 行），但要处理超时、内存、弹窗、下载拦截，
并且要串行化以免同时开一堆窗口。**只在检测到 spa 时才触发**，成本可控。
做不做取决于第 1 条（覆盖率实测）的结果——如果空壳站占比很低，就不值得做。

#### 3. RCPT 探测的成功路径从没在真实网络下跑通

`verifyEmail` 返回 `valid` 的那条分支，**开发环境从来没执行过**——
出站 25 端口在开发机上被封了，每次都走到「探测不了」。

代码逻辑是按 SMTP 标准写的，但没有一次真实的 250 响应验证过。

**要做的**：在一台 25 端口通的机器上（很多云服务器也封，要找能通的）
对已知存在和已知不存在的地址各测几个，确认状态判定正确。

#### 4. 「五分钟拿到 50 家公司」没有真做到（门槛已大幅降低，但仍不是零配置）

④ 里做的是**向导**，告诉用户每一步该点什么，但**没有解决零配置**。
真正的零配置首跑需要内置搜索额度，而在 Electron 里内置 API key 是可提取的
（用户解包 asar 就能拿到），等于把 key 送人。

**这一条仍然没解——但处境比原来好很多。** 两处解绑 Claude 之后
（`a5cc004` 官网深挖、`718be03` 竞品反查：页面由 `netprobe` 自己抓下来，
模型只负责**读已经拿到的文本**），全流程不再要求 Claude 的联网检索能力，
任何 OpenAI 兼容模型都能跑。所以门槛从"必须配 Claude 并按次付费"降到
"配一个 DeepSeek key，日常量约 ¥14/月"。

**现在的建议**：不要再追"零配置"这个说法，改成**"配一个便宜的 key 就能跑通全流程"**——
这句话现在是真的，而"零配置"在买断制 + 纯本地的架构下大概率永远做不到。
向导第一步应该直接给 DeepSeek 的申请链接和预估月成本，把这一步做成三分钟能完成的事。

仍然不建议的两条路：
- 自建中转（就有服务端了，和"纯本地"的定位冲突）
- 内置我们自己的 key（asar 可解包，等于把 key 送人）

#### 5. 追踪像素只有发射端，没有接收端

我们会在邮件里插入指向用户自己域名的 1×1 像素，但**用户得自己搭那个端点**，
而我们没有给任何说明。

**要做的**：写一份「怎么搭追踪端点」的文档，附一个能直接用的最小实现
（Cloudflare Worker / Vercel 函数各一份，二十行代码），返回 1×1 gif

没有这个，⑥ 对普通用户等于用不了。

#### 6. 开发信引用官网事实只覆盖英文首封

会出现中间夹一句英文的情况。

**要做的**：按 `prospect.market` 出对应语种的句式，或者在非英语市场下不插入。

#### 7. 抓到的"事实"太浅

现在只取 `<title>`、`meta description`、`h1-h3`。这些通常是"我们是XX公司"
这类泛泛介绍，用来做个性化的说服力有限。

**要做的**：抓产品页和新闻页的具体内容（产品型号、认证、近期动态）。

1. 打开「设置 → 隐私和安全性 → 开发者选项 → 开发人员模式」，之后正常打包
2. 手工把缓存解出来（跳过 macOS 那部分，Windows 构建根本用不到）：

     "%LOCALAPPDATA%/electron-builder/Cache/winCodeSign/<任一>.7z" \
     "-o%LOCALAPPDATA%/electron-builder/Cache/winCodeSign/winCodeSign-2.6.0" \
     "-x!darwin"

这一段要等 `publish.owner` 配成真实账号、真发一次 Release 才能测。

要么在购买页和安装指引里提前说明怎么点「仍要运行」。

### 值得记住的坑（都已修掉并写进测试，别踩回去）

1. **国内 DNS 返回残缺 TXT**。查 github.com：系统默认 8 条无 SPF、8.8.8.8 22 条有
   SPF、阿里 223.5.5.5 17 条无 SPF。据此让已配 SPF 的用户"再加一条"，两条 SPF 按
   RFC 7208 直接失效——**会亲手搞坏用户的送达率**。现在多解析器取并集 + 查不准就说查不准。

2. **没配追踪时 `opens` 恒为 0**，`cold` 分支会把所有人判成"没打开"并自动暂停全部序列。
   **测不到 ≠ 没打开**。

3. **定位校准会误伤用户自己的产品词**。卖无人机配件的人标记一家无人机工厂为不对口，
   `drone` 进排除词就等于废掉他的全部搜索。现在有 `protectedTerms()` 保护。

4. **合规筛查剥词要有分寸**。剥 `CO/LTD/GmbH` 是对的（让"少个逗号"不影响比对），
   但**不能剥** `TRADING/HOLDING/INTERNATIONAL`——那样 `ACME TRADING` 和
   `ACME HOLDINGS` 会一起压成 `ACME` 双双误报。误报和漏报一样有害。

5. **`noticedate` 是 `DD-Mon-YYYY` 文本**，按字符串比大小会算错
   （`'04-Aug-2026' < '31-Oct-2025'`）。我用它得出过一次错误结论。

6. **JS 模板字符串里的 `` 是退格符不是词边界**。`new RegExp(\`\b(...)\`)` 少一个
   反斜杠，正则里就没有词边界，规则**静默失效**（不报错、看着对、就是不生效）。
   合规筛查的剥词最后改成了 token 过滤，绕开这类转义坑。
